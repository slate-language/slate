# 2026-09-24 — A `with { … }` NAMES ITS KEYS IN THE UNIT, AS A LITERAL DOES

[`object-keys`](2026-09-23-object-keys.md) gave an object literal `MakeObject(first, n)`: its keys
are a run of `Unit.object_keys`, each arriving with the literal's own cell and the hash the unit took
when it interned the text, and `obj_put_keyed` writes them — no `PushStr` per key, no hash per key.
Its "What is left" named the other construction that writes literal keys: `base with { a: 1 }` still
compiled to a `PushStr` before every value and wrote each pair through `obj_put`, hashing the key on
every run.

## What changed

- **`WithObject(first: u32, n: u32)`** replaces `WithObject(n: usize)`. `compile_expr.sysl` lays
  the keys down with `intern_object_keys` — the same routine `MakeObject` uses — and emits only the
  values, so the instruction takes `n + 1` values (the base and the values) rather than `2n + 1`.
- **`compose_with_object`** (`run_compose.sysl`) reads key `i` as `u.object_keys[first + i]`, takes
  its cell with `literal_on` and writes the copy with `obj_put_keyed`. The copy is a fresh table,
  frozen only after its writes (a data value's copy) and never keyed by identity, which is the
  precondition `obj_put_keyed` states; its comment now says so.
- **`unknown_field_complaint` is still asked of the BASE**, once per key, with the key's cell — so a
  data value still refuses a field its declaration does not have, and a field written twice is not
  taken for one the first write added. Pinned in both suites.
- The JavaScript back end is untouched: it emits its own `with`.

Control: dev `bc0b522` (slate 0.1.6), built in a detached worktree; both sides `bench/pgo.sh`.

## The witness

`SLATE_PROFILE` on `--features profile` builds, over a `with`-heavy probe (below):

| | dev | branch |
|---|---|---|
| instructions | 87,000,029 | **81,000,029** (−6.9%) |
| `PushStr` | 6,000,001 | **1** |
| `WithObject` | 3,000,000 | 3,000,000 |

Two keys per `with`, three million `with`s: exactly the six million key pushes gone.

## Timing

**No program in `bench/` writes a `with`** (`grep -l " with {" bench/*.sl` is empty), so the suite
cannot move for this change except by layout. The timing is a probe program, not committed to
`bench/` (it would join the PGO training set and the suite's mean):

```
var p = { x: 0, y: 0, vx: 1, vy: 2, tag: "p" }
var total = 0

for i in 0..<3000000
    p = p with { x: p.x + p.vx, y: p.y + p.vy }
    total = total + p.x - p.y

print(total)
```

Alternating best-of-9, PGO against PGO, lowest of each: **683.6 → 624.5 ms, −8.6%**. The box was
~55–65% idle throughout, other agents' PGO builds and gates running — below the 85% the method
asks for, so read the figures as indicative; the probe's nine pairs had the branch faster in all nine.

The suite, `bench/alternate.pl 9` on the same two binaries in the same load: **geometric mean
−0.70%**, every row within ±5% (`fib` +4.1%, `nested` +4.6%, `startup` −4.8%, `reals` −3.4%) — PGO
layout and load noise, none of these programs building a `with`. Call it zero.

## Tests

`tests_object_keys.sysl`: a `with` pushes no key and its `WithObject` names its three keys (one
written twice) in the unit; the copy keeps the base's order and a twice-written key's last value; an
empty `with {}` names no keys and copies; a data value takes every field it has, even twice, and
still refuses `depth` after `w`; a base that is not an object is still refused.
`tests/lang/withkeys.sl` (both back ends): a changed field keeps its place, a key written twice,
`proto` written by a `with` delegates, an empty `with`, a `with` over a base past `SmallTable`, the
data-value pair above, and a non-object base.

## What is left

- **The base's own fields are still copied through `obj_put`**, hashing each key again although the
  base's entry already carries its hash. A copy that takes the entries and the index whole (the
  base's table shape, then the written keys) would remove that too; it matters only for a `with`
  over a wide object.
- The interpreter and the JavaScript back end word a non-object base differently (`copies an
  object` / `takes an object`); `withkeys.sl` asks only the shared half.
