# `gc.alloc` is one loop, and the loop is a linear scan of the bin array (dev `ff720e9`, sysl 0.0.125)

**THE 6.2% IS NOT SPREAD OVER THE ALLOCATOR — IT IS `take_larger`, WHICH WALKS UP TO 87 SIZE CLASSES
ON EVERY ALLOCATION WHOSE OWN CLASS IS EMPTY.** `sample` reports a leaf frame with a byte offset, so
the samples inside one function can be read against its disassembly, and all three of the programs the
item names agree: the largest `gc$alloc` node on each holds **95 of `alloc.sl`'s samples, 78 of
`calls.sl`'s and 49 of `csv.sl`'s**, and its two hottest program counters are `+396` and `+404` —
`0x18C` and `0x194` from the function's entry, which `otool -tv` says are

```
000000010003cc48  ldr  x11, [x12]          <- +396
000000010003cc4c  cbnz x11, 0x10003cd38
000000010003cc50  add  x13, x13, #0x1      <- +404
000000010003cc54  add  x12, x12, #0x8
000000010003cc58  cmp  x13, #0x55
000000010003cc5c  b.ls 0x10003cc48
```

six instructions, one dependent load each, bounded by `#0x55` — **`NBINS - 1`, 87**. The only other
`gc$alloc` node above `sample`'s five-sample floor is `+976`, the epilogue reached after the
`bl _bzero`, at 10 / 9 / 7 samples. There is no third place the time is.

**AND THE REASON THAT LOOP IS REACHED AT ALL IS THE COLLECTOR'S OWN COALESCING, WHICH IS WHY IT IS THE
STEADY STATE RATHER THAN A WARM-UP.** `rebuild_free` merges each run of adjacent free blocks into one,
so a wave of dead 80-byte cells comes back as a few large blocks in a HIGH class; `split` then returns
each remainder to a high class too. slate's objects are all small — a `StrObj` is 40 bytes and asks for
`align_up(40 + sizeof(Header))` = 80, which is bin 5 — so `bins[5]` is usually **empty**, `take_larger`
walks bins 6 through 87 to find the big block, splits it, and puts the remainder back out of reach of
the next allocation, which walks the eighty again.

**The fast path costs about forty instructions and the scan costs about five hundred**, which is the
whole of the answer to *what is `gc.alloc`'s hot path*: for a small object it is `align_up` + `bin_of`
(one shift) + one load of `bins[want]` + a null test, and then either ~30 more instructions of
`split`/`hand_out`/`bl _bzero`, or the 82-iteration walk in front of them.

## What the four questions were, and the four answers

| | answer |
|---|---|
| **1. what the hot path is, and how much of the 6.2% each part is** | a size-class free list, no lock, no `malloc` underneath, no threshold check — and **essentially all of the self time is `take_larger`'s linear scan** (95/78/49 samples of the 96/78/49 `gc$alloc` holds on `alloc`/`calls`/`csv`). The header write, the object-list link and the two counters are the `+976` node's 10/9/7 samples together with the `_bzero` they precede |
| **2. can the fast path be `@inline`** | **no.** `gc$alloc` is **1,080 bytes and 270 instructions** — `take_from_bin` is unrolled eight times (`SCAN`), `bin_of`'s large-class loop is written out twice, and `split` + `push_free` + `hand_out` are all inlined into it. A **split** fast path could be, and that is the proposal below |
| **3. what slate pays on top** | **two `_tlv_get_addr` calls per allocation** — the control's call graph shows `new_object + 176` and `alloc_or_collect + 56` each calling it, `current()` reading a `@thread_local` — plus `alloc_or_collect` being a real call (7 self samples on `alloc`), the **40-byte `gc.Header`** on a 40-to-112-byte object, and the `_bzero`/`_platform_memset` (7 + 15, 15, 7 samples) that every constructor immediately writes over. **This page lands the first of those**; the rest are the gc's |
| **4. the collector's share against the allocator's** | `gc$collect` + `rebuild_free` is **35 / 15 / 28** samples against the allocator's **96 / 78 / 49**, so the allocator is **1.8x to 5x the collector** on the three programs. `_xzm_free` and the `malloc_tiny` family are sysl's `Buf`/`Map` storage under the objects, not the collected heap |

## What landed here, which is slate's half and is small

**An allocation reads the VM once.** Every constructor in `obj.sysl` used to ask `current()` three
times — once at the call site for the reserve (`ptr_cast(current().spare_str)`, evaluated eagerly), once
inside `alloc_or_collect` for `slate_heap()`, and once for `charge` — and `current()` is a
`@thread_local` read, which on macOS arm64 is an indirect call into the dynamic loader rather than a
load. `alloc_or_collect` takes a `*Vm` and uses `&v.heap`; `charge_on(v, n)` is `charge` for a caller
that already holds one; the ten constructors take `val v = current()` at the top. It is the `vm-param`
pattern (`b12a193`) applied to the allocation path.

## THE PROPOSAL FOR `sh.sysl.gc`, WHICH IS WHERE THE 6.2% ACTUALLY IS

Three lines, and the exact functions are `take_larger` and `push_free`/`take_from_bin` in
`sh/sysl/gc/gc.sysl` (0.2.3, lines 185–234), plus two fields on `struct Heap` (line 151) and its
constructor `heap` (line 344).

1. **`struct Heap` grows a two-word bitmap of the non-empty classes** — 88 bins, so `mask_lo: u64` and
   `mask_hi: u64` — maintained at the four places `h.bins[...]` is assigned: `push_free` (set),
   `take_from_bin`'s unlink (clear where the head went null), `take_larger`'s unlink (same), and
   `rebuild_free`'s clearing loop (both to zero, the rebuild's own `push_free` calls refilling them).
2. **`take_larger` becomes a bit scan**: `mask_lo >> (b + 1)`, `trailing_zeros()` (sysl's
   `sysl.math.integer` has it, and it is `ctz` on arm64), falling through to `mask_hi`. The 82-iteration
   dependent-load walk becomes a shift, a compare and a count — **O(1) in place of O(NBINS − want)**.
3. **And `h.steps += 1` is a read-modify-write on the heap inside the scan that succeeds** — a
   diagnostic counter `alloc_steps` exposes for a test — so it is worth asking whether it belongs
   behind a feature. It is second order beside item 2 and should be measured after it, not with it.

**Expected gain**: the sampled profile says `gc.alloc` is 6.23% weighted and that ~99% of its self time
is the scan, so the ceiling is about **6% of the geometric mean**, and 20 to 28% of `alloc`, `calls` and
`csv` each. That is by far the largest single item any of the four profiles has named, and it is
entirely inside one package.

**What is NOT proposed, and why**: the 40-byte `Header` in front of a 40-byte `StrObj` is 50% overhead
on slate's commonest cell and inflates `need`, the class it lands in and the `_bzero` — worth a separate
look, but it is a format change reaching the sweep, `rebuild_free` and every offset. And an `alloc_raw`
that skips the zeroing would suit every slate constructor (each writes all its fields immediately) but
would weaken the guarantee `gc.alloc` currently makes about storing a counted member, which is a
decision for the package's author rather than a performance item.

**This page measured none of that**, and says so rather than guessing: a vendored copy of the package
was patched to price item 2 end to end and the attempt was refused as a write to a shared resource. The
mechanism is settled by the disassembly and the sampled offsets; the number is not.

## The tests

Two in `tests_payload.sysl`, and both are about the seam this change threads rather than about speed —
an allocation is charged to the VM it was made in, and the VM that fills its heap is the one that says
so:

- `A_VALUE_MADE_WHILE_A_SECOND_VM_IS_ENTERED_COMES_OUT_OF_THAT_VMS_HEAP_AND_IS_CHARGED_TO_IT` — a
  string built while a second VM is current moves that VM's `payload` and `gc.used`, and moves neither
  of the program's own.
- `A_SECOND_VM_THAT_FILLS_ITS_HEAP_SAYS_SO_ABOUT_ITSELF_AND_ANSWERS_WITH_ITS_OWN_RESERVE` — the error
  path of the same seam: strings held on the shadow stack until a 256 KiB heap is full, then
  `heap_exhausted` true on that VM, the reserve rather than null handed back, and the program's own VM
  untouched.

## How the offsets were read, since it is the part worth keeping

`sample`'s **call graph** prints a leaf as `symbol + offset,offset,… [0x…,0x…]` where the collapsed
self-time table prints only the symbol. So attribution **inside** a function is available from the
ordinary sampler with no extra tooling: take the load address off the report's header (or any
`+ 4` frame), subtract, and look the result up in `otool -tv`. That is how a figure that had been a
function's name for four profiles became a six-instruction loop.
