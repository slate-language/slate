# 2026-09-23 — A ROW OF BARE NAMES IS TAKEN APART BY THE INSTRUCTION — profile 5's item 4

Profile 5's item 4, the last of the matcher items and what `match-leaf` left behind. `for [a, b] in
pairs` used to enter the pattern matcher once a turn — `match_walk`, then `match_array`, then
`match_leaf` per name — push what it bound onto the operand stack, and have `lay_bindings` copy that
run back down into the cells the compiler had already claimed for it. **A pattern that is a row of
BARE NAMES cannot half-match**: every part is a name and a name takes whatever stands in its place,
so there is nothing for the matcher to decide, nothing to gather and nothing to copy. `UnpackFixed`
writes the cells straight out of the subject and the matcher is never entered.

Control `5484870` (dev, slate 0.1.2, sysl 0.0.126); branch `for-head`.

## What changed

**One new instruction, `UnpackFixed(w: u32, object: bool)`.** `Unit.wide` carries `a` the pattern,
`b` the first of the slots and `c` how many names it binds — a two-`u32` payload, which is what a
32-byte `Ins` allows (`narrow-ins`). `object` says which of the two shapes it takes apart:

- an **array** pattern, closed, with no rest, no default and every item a bare name: the subject must
  be an array of exactly `c` elements, and element `i` goes into slot `first + i`;
- an **object** pattern with no default and no `?`, every value a bare name: each key is read through
  `field_through` — the proto chain included, exactly as `match_object` reads it — and lands in slot
  `first + i`, key order being `pattern_names`' order and therefore the order the cells were claimed.

**Anything else still walks**: a default, a `?`, a rest, an open head, a literal, a nested pattern, a
binding one of whose names is KEPT in the scope (that one takes `Unpack`, as it always did).

**The two halves are written together in `match.sysl`** — `unpack_op` decides which instruction a
binding site gets and `unpacked_fixed` is what the instruction runs — because which patterns may skip
the matcher and how they are then taken apart are one rule, and they share `unpack_complaint` for the
sentence a subject that does not fit is owed. `slots.sysl`'s `bind_pattern` asks `unpack_op` for the
op and is otherwise unchanged; `run_frames.sysl` gains one arm inside the hot block, next to
`UnpackSlots`.

**IT IS A BINDING SITE'S RULE AND NOT A `for` HEAD'S, WHICH COSTS NOTHING AND REACHES MORE.**
`bind_pattern` is the one place that decides how a pattern binds, so `val { a, b } = p` and a
parameter that unpacks take the same instruction as the loop head the item was named for.

**THE SENTENCE IS THE MATCHER'S OWN AND THAT IS BY CONSTRUCTION.** The instruction keeps the pattern
index precisely so a subject that does not fit is answered by `unpack_complaint(pat, subject)` — the
same function the `UnpackSlots` path calls, reached from the same `fault`. `tests_pattern.sysl` pins
five of those sentences, three of them new: a head given a longer array, a head given an integer, and
an object head whose field is missing.

## The counts

`sysl build . --features profile`, `SLATE_PROFILE=1` on each program, control and branch:

| program | instructions | before | after |
|---|---|---|---|
| loops | 64,138,039 both | `UnpackSlots` 8,000,000 (12.4%) | `UnpackFixed` 8,000,000 (12.4%) |
| nested | 84,108,048 both | `UnpackSlots` 6,000,000 (7.1%) | `UnpackFixed` 6,000,000 (7.1%) |
| dispatch | 140,000,026 both | neither | neither |

**One instruction replaces one instruction**, so the totals are identical to the instruction and no
profile-count test needed a number changed. `dispatch` has no destructuring binding at all — its
`match_leaf` share is `match` ARMS, which is `TestSlots` and is not this item — so it was measured
only to say so.

**The ceiling on the shortlist was 1–1.5% and what it took is about 3%.** The two rows the item named
move by far more than its share of the mix predicted, which is the reading to expect when an item
removes a *call graph* rather than an instruction: what came off `loops` is `match_walk`,
`match_array`, two `match_leaf`s, two stack pushes, a `lay_bindings` loop and a truncate, per turn.
`closures` and `csv` read slower in both runs and hold no destructuring binding between them — that is
this instrument's floor for a change that moves code around, and the same pair drifted the same way on
`match-walk`.

`bench/run.sh -n 5`: the geometric mean against Lua goes **3.6x → 3.5x**, `loops` **2.6x → 1.7x** and
`nested` **3.8x → 3.1x**; against `node --jitless` `loops` goes 0.6x → 0.4x.

## The tests

- **`tests_slots.sysl`** — three tests reading the emitted instruction names off the chunk, which is
  the question no answer can settle: a two-name head, a three-name head, an object head and a
  destructuring `val` take `UnpackFixed` and no `UnpackSlots`; a default, a rest, a nested head, an
  open head and a head holding a literal all keep `UnpackSlots` and take no `UnpackFixed`; and a head
  one of whose names a closure reaches takes neither, the scope path being `Unpack`.
- **`tests/lang/control.sl`** — six tests on both back ends: a head of two and of three names, an
  object head (including a field supplied by a proto and a field the head does not name), the three
  shapes that still walk, a head over a map's pairs, and an object head shadowing an outer name. A
  head whose element does not fit faults on both — the sentence is pinned in sysl rather than here,
  the JavaScript runtime having its own wording for an unpack that fails.
- **`tests_pattern.sysl`** — the five complaints above.

`757 passed` on `slate test tests/lang` and on `slate test --js tests/lang`.

## What is left

Nothing of the matcher group that this item can reach. `match_leaf` stays where a `match` arm tests a
pattern (`TestSlots`) and where a nested or defaulted binding still walks, which is the shape the
remaining share is made of. The shortlist's items 3 and 5 — threaded dispatch and a register machine —
are what is left of the dispatch head.
